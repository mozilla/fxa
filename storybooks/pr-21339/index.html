Summary
fix(auth-server): emit opaque session-token handles, not raw sessionTokenId [FXA-14056]
Description
Because:
 - The attached-clients and devices-and-sessions endpoints returned the raw
   sessionTokenId to clients. With server-side Hawk MAC verification no longer
   enforced, a raw sessionTokenId is effectively a bearer credential, so
   emitting it is a token-disclosure risk.

This commit:
 - Adds computeSessionTokenHandle (HMAC-SHA256 over "<uid>:<sessionTokenId>",
   keyed by a new SESSION_TOKEN_HANDLE_KEY config) to derive a one-way,
   uid-bound handle that cannot be recovered or replayed as a Hawk id.
 - Guards the key in production via SECRET_SETTINGS so an unset
   SESSION_TOKEN_HANDLE_KEY cannot silently fall back to the in-repo default.
 - Returns the handle in place of the raw sessionTokenId on the attached-clients
   and sessions endpoints; the sessions list now also requires a verified
   session.
 - Migrates /session/destroy to accept customSessionTokenHandle, resolving it
   back to the caller's own session token (scanning their sessions and matching
   the recomputed handle) so no client-facing API is keyed on a raw id.
 - Updates fxa-auth-client, fxa-settings, fxa-shared factories, swagger docs,
   and the corresponding unit and remote tests.
