Summary
fix(settings): fail closed on the pairing approval TOTP gate
Description
Because:
- The React /pair/auth/allow TOTP gate failed open three ways: it trusted
  a forgeable location.state.totpComplete, swallowed accountProfile errors
  and rendered the approve button anyway, and skipped the check entirely
  when web localStorage held no sessionToken. The Backbone gate it replaced
  failed closed.
- Sourcing the account from localStorage was itself a bypass: signing a
  second, non-TOTP account into the web app in the same Firefox made the
  check pass while pairAuthorize still paired the browser's account.
- Pairing has no server-side backstop — the grant carries no acr_values and
  sync scoped keys require only a verified session — so this client check is
  the only second factor between someone at an unlocked, signed-in Firefox
  and a persistent Sync device on the account.

This commit:
- Adds lib/pairing-authority.ts: reads the account being paired from the
  browser over the fxa_status WebChannel (Backbone parity with
  shouldSetSignedInAccountFromBrowser) and tracks TOTP step-up in memory,
  keyed by channel_id, replacing the forgeable router state.
- Makes AuthAllow fail closed: no browser account or an unreadable TOTP
  status cancels pairing to /pair/failure, TOTP without an accepted code for
  this channel redirects to /pair/auth/totp, and the approve form renders
  only once the gate passes. handleSubmit re-checks before authorizing.
- Verifies the code in AuthTotp against the browser's session token and
  records the verification per pairing channel.
- Keeps the always-prompt-when-TOTP-enabled semantics rather than accepting
  an already-AAL2 session, which would let the borrowed-browser attacker
  skip the prompt outright.
- Adds unit coverage for the gate, the new lib, and the AuthTotp submit
  paths.

Server-enforced AAL2 on the pairing grant remains the durable fix; it needs
acr_values from the supplicant browser and a decision on pre-2FA sessions
that hold sync scoped keys.
