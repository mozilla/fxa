Summary
bug(auth-server): Let clients opt out of the server-sent signin OTP
Description
Because:
- Dormant accounts signing in through Settings received two identical OTP
  verification emails. The auth-server sends one from `sendSigninNotifications`
  during `/account/login`, and `handleNavigation` sends a second via
  `sessionResendVerifyCode` as it routes to the code screen.
- The server-side send is the redundant one. It was added as a stop-gap for RPs
  that integrate with the API directly and never render our web UI, and it has
  caused duplicate-email problems ever since. The client-side send is the one we
  want to keep: it couples the email to the navigation that prompts for the code.

This commit:
- Adds an optional `suppressSigninVerificationEmail` payload flag to
  `/account/login` and `/session/reauth`. When set, `sendVerifyLoginCodeEmail`
  short-circuits, covering both the unverified-session (`sendVerifySessionEmail`)
  and unverified-account (`sendVerifyAccountEmail`) OTP paths. Link-based
  confirmation emails are deliberately unaffected — they have no client-driven
  equivalent, so suppressing them would drop mail on the floor.
- Sends the flag from the fxa-settings password and unblock sign-in paths, the
  flows that reach `handleNavigation` and send the code themselves.
- Removes the `sendVerificationEmailFromClient` gate, so `handleNavigation` is
  once again the sole sender for our own front-end.
- Leaves legacy behavior intact for clients that omit the flag. They will not
  update their code, so the auth-server keeps sending for them exactly as today.

Note: the server treats `email-2fa` and `email-otp` identically, but
`handleNavigation` only sends for `email-otp`. Settings only ever requests
`email-otp`, so this is inert today, but it is a trap if that changes.

Closes #FXA-14109
