Summary
fix(settings): destroy the browser session token on sign-out
Description
## Because

- A web RP that forces sign-in (`prompt=login`) makes Settings store a new session token over the one it shares with Firefox.
- Settings sign-out destroyed only the stored token and then sent `fxaccounts:logout`. Firefox signs out locally only, so the browser session, with its device record, stayed live.

## This pull request

- `DropDownAvatarMenu` asks the browser for its token with `fxa_status` (`requestSignedInUser`). If the uid is the same and the token differs, it calls `authClient.sessionDestroy` on that token. The call runs after `session.destroy()` and before `fxaLogout`.
- The new call ignores errors, so sign-out still completes. The browser is not asked outside Firefox.
- Adds unit tests in `DropDownAvatarMenu/index.test.tsx` and a functional spec in `fxaStatus.spec.ts`. `useAuthClient()` throws without `authClient` in context, so the `HeaderLockup` and `SettingsLayout` tests pass `mockAppContext()`.
- Round 2: the ordering test now also asserts that `session.destroy` runs before `authClient.sessionDestroy`. The 12 stories that render `SettingsLayout` with no `AppContext.Provider` now get one with `mockAppContext()`, so `useAuthClient()` does not throw.
