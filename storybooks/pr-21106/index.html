Summary
fix(tests): drop throwaway MySQL schemas after integration suites
Description
## Because

- `testAccountDatabaseSetup` creates a `testAccount-<uuid>` schema per spec file and never drops it. Closing the connection pool does not drop a schema.
- So a local MySQL gains one schema per spec file per run. One developer machine had 184 of them before anyone noticed. CI is not affected.

## This pull request

- Adds `testAccountDatabaseTeardown(db?)` to `tests.ts` and exports it from the lib index. It asks the connection for its own schema with `SELECT DATABASE()`, drops that schema only if the name starts with `testAccount-`, then closes the pool in a `finally` so a failed drop cannot leak connections.
- Calls the teardown from `afterAll` in the 12 `.in.spec.ts` files that call the setup. Jest runs `afterAll` whether the tests pass or fail, so failing runs clean up too.
- Sweeps `testAccount-*` schemas older than `ORPHAN_SCHEMA_MAX_AGE_HOURS` (3 hours) at the start of `testAccountDatabaseSetup`, based on `information_schema.TABLES.CREATE_TIME`. That covers a crash or a Ctrl-C, where no hook gets to run. The sweep is age based rather than sweep all, so it cannot take a schema out from under a concurrent run, and it warns instead of throwing if two parallel suites race for the same orphan.
- Moves the hook in `backup-code.manager.in.spec.ts` from `afterAll` to `afterEach`. That file calls the setup in `beforeEach`, so with `afterAll` it still left four schemas per run.
- Leaves the `testAccountDatabaseSetup` signature and return value alone, so no call site had to change.
