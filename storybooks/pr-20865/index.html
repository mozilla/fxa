Summary
bug(auth-server): Let FxA's front-end turn off the server-sent signin OTP
Description
Because:
- Dormant accounts signing in through Settings received two identical OTP
  verification emails. The auth-server sends one from `sendSigninNotifications`
  during `/account/login`, and `handleNavigation` sends a second via
  `sessionResendVerifyCode` as it routes to the code screen.
- The server-side send is the redundant one. It was added as a stop-gap for RPs
  that hit this API directly instead of going through our web UI, and it has
  caused duplicate-email problems ever since. The client-side send is the one
  worth keeping: it couples the email to the navigation that prompts for the code.

This commit:
- Adds an optional `sendSigninVerificationEmail` payload flag to `/account/login`
  and `/session/reauth`, defaulting to `true` when omitted.
- Honours the flag in `sendVerifySessionEmail` only — the unverified-session path
  that produces the duplicate. The unverified-account path
  (`sendVerifyAccountEmail`) keeps sending unconditionally, because the client's
  stand-in `/session/resend_code` sends a *different* template
  (`verifyShortCode`) when the primary email is unverified. Honouring the flag
  there would silently change which email a signing-up user receives rather than
  just deduplicating.
- Passes `false` from FxA's own front-end only: the fxa-settings password and
  unblock sign-in paths, which reach `handleNavigation` and send the code
  themselves. FxA is the party turning it off.
- Removes the `sendVerificationEmailFromClient` gate, so `handleNavigation` is
  once again the sole sender on /signin_token_code for our own front-end.
- Changes nothing for anyone else. Direct API consumers omit the flag, get the
  `true` default, and keep the server-sent email exactly as today — including the
  RPs that render their own verification UI, which is what this send is there for.

Note: the server treats `email-2fa` and `email-otp` identically, but
`handleNavigation` only sends for `email-otp`. Settings only ever requests
`email-otp`, so this is inert today, but it is a trap if that changes.

Closes #FXA-14109
