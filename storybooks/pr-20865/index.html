Summary
test(functional): Assert signin verification email counts
Description
Because:
- FXA-14109 was a duplicate-email bug, and the regression introduced while
  fixing it was a wrong-template bug. Neither is visible to unit tests, which
  assert `toHaveBeenCalledTimes(1)` on a mailer mock rather than checking what
  actually lands in a mailbox.
- The regression surfaced in CI only as four `EmailTimeout` failures in
  unrelated-looking specs, which took a full pipeline and a log dig to diagnose.

This commit:
- Adds three Playwright tests to `tests/signin/signIn.spec.ts` that assert email
  counts directly, so a future change to this logic fails with a legible message
  instead of a timeout.
- "forced signin confirmation sends exactly one verifyLoginCode email" covers the
  reported dormant-account case: a `sync`-prefixed account (matched by
  SIGNIN_CONFIRMATION_FORCE_EMAIL_REGEX) signs into Settings and must receive
  exactly one code email, not one per sender.
- "unverified signin keeps the server-sent verifyLoginCode email" pins the reason
  the flag is scoped to `sendVerifySessionEmail`. Widening it back to the shared
  helper drops this email and leaves only the client's `verifyShortCode`.
- "servicesWithEmailVerification RP gets exactly one verifyLoginCode email" covers
  the config-list path, where a disagreement between server and front-end would
  leave the user with no code at all. No existing test exercised it: the VPN specs
  use the Fenix client with `service=vpn`, but the list matches on client IDs.

Notes:
- Each test uses a later email in the same flow as a causal barrier rather than a
  fixed sleep, because counting as soon as the first email lands would pass even
  when a duplicate is in flight — a false green.
- Codes are read via `waitForEmail(..., EmailHeader.*)` rather than
  `getVerifyLoginCode()`, which clears the whole inbox and would destroy the
  evidence being counted.
- The two `sync`-prefix tests are local-only; that regex is not set on stage.

Verified each test fails against the bug it guards (2 instead of 1, and 0 instead
of 1 respectively) and passes once restored. Full file: 8 passed, 1 pre-existing
skip. Stability checked with --repeat-each=3.
