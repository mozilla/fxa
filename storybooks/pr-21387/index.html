Summary
fix(settings): route /pair on desktop only after fxa_status answers
Description
Because:

- The 500ms pairing deadline in useFxAStatus settled Firefox desktop on pairing version 1 whenever the browser answered late, and the v1 bootstrap hard-navigated before the real reply could win
- The web channel started its reply timeout before the message was sent, and Firefox pauses requestAnimationFrame in hidden tabs, so /pair tabs opened in the background timed out without ever asking

This commit:

- exempts Firefox desktop from PAIRING_FXA_STATUS_TIMEOUT_MS so it waits on firefox.fxaStatus's own retries
- reports 'unanswered' when firefox.fxaStatus exhausts its attempts
- starts the web channel reply timeout inside the frame that sends the message and drops the listener on timeout
- covers the desktop case, the exhaustion state and the frame-gated timeouts in tests
