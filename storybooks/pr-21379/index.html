Summary
fix(settings): destroy the replaced web session on re-sign-in
Description
## Because

- A second sign-in to the same account at the same browser left the first web session live on the auth server.
- `storeAccountData` in `storage-utils.ts` overwrote `accounts[uid].sessionToken` and did not destroy the old token. The sign-in and sign-up pages call it.

## This pull request

- Makes `storeAccountData` read the old token first. If the new token is different, it calls a new helper, `destroyReplacedSession`, and does not wait for it.
- Outside Firefox, the helper calls `sessionDestroy` with the old token.
- In Firefox, the helper first sends `fxa_status`. It keeps the old token if there is no reply, or if `signedInUser.sessionToken` matches it. Otherwise it destroys the token.
- The helper catches every error. A failed destroy never blocks sign-in.
- Leaves `persistAccount` unchanged, because `components/App` uses it to adopt the browser's token.
- Uses a plain `AuthClient(config.servers.auth.url)` for `sessionDestroy`, because `storage-utils` cannot reach the AuthClient in the React app context. This also skips the app error handler. On a Settings path, that handler marks the user signed out on a 401, and the old token can give a 401.
- Sends `fxa_status` with service `sync`. Firefox returns `signedInUser` in private browsing only for sync. Without it, the code could destroy the token that the browser holds.
- Adds `storage-utils.test.ts` (6 tests) and a functional test in `tests/oauth/signin.spec.ts`.
