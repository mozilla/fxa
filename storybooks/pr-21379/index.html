Summary
fix(settings): destroy the replaced web session on re-sign-in
Description
## Because

- A second sign-in to the same account in the same browser left the first web session live on the auth server.
- `storeAccountData` in `storage-utils.ts` replaced the stored `sessionToken` and did not destroy the old token.

## This pull request

- Makes `storeAccountData` read the old token first. If the new token is different, it calls a new helper, `destroyReplacedSession`, and does not wait for it.
- Outside Firefox, the helper calls `sessionDestroy` with the old token.
- In Firefox, the helper first sends `fxa_status`. It keeps the old token if there is no reply, or if `signedInUser.sessionToken` matches it. Otherwise it destroys the token.
- Sends `fxa_status` with service `sync`. Firefox hides `signedInUser` in private browsing unless the service is sync.
- Catches every error in the helper. A failed destroy never blocks sign-in.
- Leaves `persistAccount` unchanged, because `components/App` uses it to refresh the token from the browser.
- Uses a plain `AuthClient(config.servers.auth.url)` for `sessionDestroy`.
- Adds `storage-utils.test.ts` (6 tests) and a functional test in `tests/oauth/signin.spec.ts`.
- Addresses review: the functional test moves out of `severity-1 #smoke` into a `severity-2` describe, so it does not run against stage and production. The catch comment is corrected. The unit tests mock `navigator.userAgent` instead of `isProbablyFirefox`.
